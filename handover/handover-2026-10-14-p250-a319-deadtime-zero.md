# П250, ночь 13→14.10.2026 — `A319`: прибор с `DeadTime() = 0` и собственным живым временем

Полоса ночного захода. Строка реестра `A319` плюс добавка распорядителя (находки ревизии
сегодняшних коммитов в тех же файлах): скорость счёта панели у `AmplitudaSerial`, оценка
завышения мёртвого времени, запятая в инструкции прибора.

## Постановка

`A319`, дословно из реестра: прибор, который сам мерит живое время, отдаёт `DeadTime() = 0`;
ядро читает ноль как «мёртвого времени нет». Три следствия: панель скорости счёта показывает 0 %
мёртвого времени; меню «Поправка на мёртвое время» ставит живое = реальному и стирает время
блока; диалог выбора прибора не предлагает конфигурацию документа.

**Решение Amber 13.10.2026 вопросником, дословно: «Чинить ночью так (Рекомендую)»** — меню при
`DeadTime() = 0` живое время не трогает и говорит человеку, что поправка для этого прибора не
нужна (живое время от прибора); панель скорости счёта считает мёртвое время по живому и
реальному времени спектра, когда живое меньше реального.

## Что сделано

* `CountsRateManager.GetDeadTime` — при τ = 0 доля берётся из времён спектра:
  новый `SpectrumDeadTimePercent` = 100·(реальное − живое)/реальное; 0, если живого нет
  (LiveTime = 0 — «не задано»), реального нет или живое не меньше реального. Конфигурации нет —
  0, как было. τ ≠ 0 — прежний текст, `DeadTime()` зовётся один раз вместо двух (метод чистый у
  всех приборов — число то же, проба сличает побитово).
* `CountsRateManager.ApplyDeadTimeCorrection` (новый, без окон) — решающая часть меню: τ ≠ 0 —
  `Calculate(T, N, τ)` как было, возврат true; τ = 0 или конфигурации нет — живое не трогается,
  возврат false.
* `MainForm.ApplyDeadTimeCorrectionStripMenuItem_Click` — зовёт его; при false — окно
  «Сообщение» с новой строкой `MSGDeadTimeCorrectionNotNeeded` (имя конфигурации, живое и реальное
  время спектра, `f1`, инвариантная культура), документ не помечается изменённым.
* `SelectDeviceDialog`:
  - новый `PreselectGuid` — предлагается конфигурация документа, если она есть в списке, без
    прежнего условия τ ≠ 0. **Почему так, а не «оставить как есть»:** прежде документ прибора с
    нулём получал ПЕРВУЮ конфигурацию списка — у Amber это «RC-103» (5 мкс), чужой прибор, и
    «Применить» не глядя пересчитывало живое время по чужому τ. Теперь первой стоит своя, и её
    «Применить» даёт честное «поправка не нужна»; чужую человек по-прежнему выбирает сам.
  - найдено и починено попутно (свой файл, минуты): закрытие окна КРЕСТИКОМ возвращало
    предвыбор как выбор (поле ответа и предвыбора было одно) — меню применяло поправку, которую
    человек отменил; ответ теперь только от «Применить». Выбор искался по ИМЕНИ — при двух

    без выбора шло дальше к `SelectedItem.ToString()` — теперь выходит.
* `DCCountRateView` — подсказка над «Мёртвое время» (`CountRateDeadTimeHint`): каким из двух
  способов считается число и что во время набора у такого прибора оно завышено. Перенос по

### Почему панель считает по всему спектру, а не на окне

Окно честно не восстановить. История скорости счёта (`CountRates`) живого времени не хранит, а
у `AmplitudaSerial` живое время приходит ступенькой раз в цикл опроса (период опроса + чтение
блока ≈ 3 + 2.5 с), тогда как реальное идёт непрерывно: на окне в 3 с (умолчание панели) доля
прыгала бы между 0 и 100 %. По всему спектру число совпадает с «Мёртвое время %» панели
измерения (`DCControlPanel.ShowRecordingStatus` считает ту же формулу) — две панели одного окна
показывают одно число. Это и сказано в подсказке.

### Завышение во время набора (добавка распорядителя, п. 2)

Живое время берётся из заголовка блока, который читается первым (статус → заголовок →
страницы, `AmplitudaSerialLine.ReadJob`), а на экран приходит после всех страниц; реальное идёт
по часам ПК непрерывно, следующее чтение начинается через период опроса Δ после конца прежнего
(`AmplitudaSerialAcquisition`: `NowMs - lastReadDoneMs >= pollMs`). Реальное время обгоняет
момент, к которому относится живое, на t_чт … Δ + 2·t_чт, и ещё ±0.5 с от целых секунд живого.
Завышение доли — от (1 − d)·(t_чт − 0.5)/T до (1 − d)·(Δ + 2·t_чт + 0.5)/T; при Δ = 3 с,
t_чт = 2.5 с (1024 канала), d = 0.3: до 9.9 пункта при T = 60 с, до 1.0 при T = 600 с; t_чт растёт
с числом страниц (512 каналов на страницу). Прежняя оценка в комментарии ((1 − d)·Δ/T) была
занижена — исправлена. Учесть это в панели честно нельзя: момент чтения заголовка знает только
`AmplitudaSerialAcquisition` (файлы полосы П249), а поправка разошлась бы с панелью измерения.
У остановленного и загруженного спектра число точное.

## Добавка распорядителя, п. 1 — скорость счёта `AmplitudaSerial` мигала

`GetCPS` и `GetSpecEffRatio` брали окно по снимкам истории (раз в ≥ 1 с), а данные блока
приходят ступенькой раз в цикл ≈ 5.5 с (подтверждено чтением: следующее чтение — через период
опроса ПОСЛЕ конца прежнего). Окно в 3 с ловило ступеньку через раз.

Выбрано: **концы окна — на моментах прихода данных** (снимки истории, на которых число отсчётов
сменилось); начало — последняя смена не позже «конец − окно», пока такой нет — самая ранняя.
Охват — целое число циклов, не короче окна, поэтому ступенька его не делит. «Окно не короче
цикла» без выравнивания не помогает: число ступенек в окне всё равно скачет на единицу
(при окне 30 с прежний расчёт гулял 0.906…1.147). Остаётся только шаг истории: каждый конец
опаздывает на долю шага (≤ 1.15 с), на охвате S число гуляет до ±шаг/S. Признак «блок молчит»
сохранён: если после последнего прихода прошло больше двух окон и двух самых длинных промежутков
между приходами на охвате — 0, как показывал прежний расчёт. Признак ступенчатости — по
контроллеру (`IDeviceLiveTimeSource`), а не по данным: поток с редкими отсчётами тоже стоит между
ними, а у него расчёт обязан остаться прежним. Приборы с потоковыми данными — прежний текст.

`GetSpecEffRatio` у такого прибора берёт те же концы (у `AmplitudaSerial` неучтённых нет — 0
всегда; в пробе подставлено 2 %, чтобы мерить).
