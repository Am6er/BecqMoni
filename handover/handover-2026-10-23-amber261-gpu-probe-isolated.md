# AMBER261 — кнопка «Матрица отклика...» роняла приложение молча (23.10.2026)

## Постановка

Amber 23.10.2026, консоль, дословно: «При нажатии на кнопку "матрица отклика" приложение аварийно
завершает работу. Никаких необработанных исключений, ни сообщений в логе нет. Возможно это как-то
связано с проверками GPU. Посмотри.»; следом: «Это у стороннего пользователя».

Вопросником того же дня, дословно: способ — **«Отдельный процесс (Рекомендую)»**; выпуск —
**«Только коммит»** (версию не поднимать).

Посреди работы Amber прислала запись журнала Windows с машины пользователя (событие .NET Runtime
1026): `System.AccessViolationException` в `RmGpu.Probe(System.String)` ←
`ResponseMatrixForm.ProbeGpu()` ← `ResponseMatrixForm..ctor` ← `DeviceConfigForm.efficiencyMatrixButton_Click`.
Это тот же стек, что ниже дал контроль на прежней сборке.

## Причина

Окно матрицы при открытии зовёт `RmGpu.Probe` в процессе приложения: `LoadLibrary(rmgpu_f.dll)`,
`rm_build_info`, `rm_probe` (рантайм CUDA → драйвер NVIDIA). Сбой в этом нативном коде (нарушение
доступа, переполнение стека) .NET 4 считает исключением испорченного состояния: его не ловят ни
`catch (Exception)` пробы, ни `Application.ThreadException`, ни `AppDomain.UnhandledException`
(журнал приложения `A113`). Процесс умирает без окна и без строки в журнале. Остаётся только
событие 1026 в журнале Windows.

Где именно падает у пользователя (`LoadLibrary`, `rm_probe` или драйвер), событие 1026 не говорит:
кадр один, `RmGpu.Probe`. Теперь журнал приложения называет последний начатый нативный вызов.

## Правка

* `RmGpu.ProbeIsolated` (`EfficiencyMaker/GpuMatrixRun.cs`): проба дочерним процессом. Ребёнок —
  само приложение (`typeof(RmGpu).Assembly.Location`, под пробой оснастки это тоже exe приложения)
  с ключом `--gpu-probe "<путь>"`. Ответ — строки «ключ=значение» в stdout с замыкающей `end=1`;
  перед каждым нативным вызовом — `step=<вызов>` со сбросом буфера. Ненулевой код выхода — причина
  `ProbeCrashed` с кодом (`0xC0000005`, `0xC00000FD`) и последним шагом. Нет ответа за 15 с —
  ребёнок снимается, причина `ProbeTimeout`. Ребёнок гасит окно отчёта Windows о сбое
  (`SetErrorMode(SEM_NOGPFAULTERRORBOX…)`): пока оно висит, упавший процесс жив.
* `Program.Main`: ключ `--gpu-probe` обрабатывается раньше всего (без проверки второго экземпляра,
  журнала и окон). Тело приложения вынесено в `RunApplication`, поэтому в сторож `check_headless.py`
  ключ разрешения `Program.Main` → `Program.RunApplication`.
* `ResponseMatrixForm.ProbeGpu`: дочерняя проба один раз за сеанс (статический кэш) и строка в
  журнале приложения `Response matrix: GPU check (child process, N s): …`. Две новые подсказки галки:
  `ResponseMatrixGpuProbeCrashed`, `ResponseMatrixGpuProbeTimeout` (en/ru).
* Попутно, тот же путь: код 35 при драйвере 0 (драйвера NVIDIA нет вовсе) теперь `NoDevice`
  «no NVIDIA driver installed». Прежде подпись говорила «драйвер Nvidia (0.0) старее рантайма
  CUDA 13.4», то есть врала на машине без карты NVIDIA.
* Счёт на GPU (`new RmGpu`, `rm_init`, `rm_run`) остаётся в процессе приложения, как решено
  вопросником; до него доходит только машина, где проба прошла.
* `GpuAppProbeP253 --mode=isolated[=<dll>]` — дочерняя проба из оснастки.

## Дополнение: причина — статический рантайм CUDA 13.4 без драйвера (`AMBER262`)

Вопрос Amber 23.10.2026, дословно: «Возможно ли, что это связано с тем, что изначально эта библиотека
была написана под Cuda12, а потом пересобрана под Cuda13? А у пользователя может вообще не быть Cuda.»

Паспорта поставочной `rmgpu_f.dll` по выпускам (`rm_build_info`):

| выпуски | паспорт |
|---|---|
| 2026.10.07.05 … 2026.10.19.01 | `phys=26; cudart=12080` (CUDA 12.8) |
| 2026.10.20.01 … 2026.10.22.01 | `phys=27; cudart=13040` (CUDA 13.4) |

Пользователю CUDA Toolkit не нужен: рантайм вшит в DLL (импорт — только `KERNEL32.dll`). Драйвер он ищет
сам: `LoadLibraryExA("nvcuda.dll", flags=0x800)` — `LOAD_LIBRARY_SEARCH_SYSTEM32`, каталог приложения
не смотрится (чужой `nvcuda.dll` рядом со стендом не подхватился).

Опыт — нативный стенд без .NET (вызов `rm_probe` поставочных DLL обоих выпусков; исходники в
`D:\BqMoni_Claude\amber261q\`, вне git):

| условие | CUDA 12.8 (выпуск 2026.10.19.01) | CUDA 13.4 (выпуск 2026.10.22.01) |
|---|---|---|
| драйвер есть (RTX 3070, драйвер 13.4) | `rm_probe=0`, устройство найдено | `rm_probe=0`, устройство найдено |
| **драйвера нет вовсе** — у DLL перехвачен `LoadLibraryExA`, на `nvcuda` ответ 126 | `rm_probe=35`, драйвер 0, «CUDA driver version is insufficient…» — штатный отказ | **процесс умер `0xC0000005`** после двух попыток загрузить `nvcuda.dll` |
| драйвер не загружается — заглушка `nvcuda.dll` из System32 есть, реализация не грузится (`SetDefaultDllDirectories` только на каталог стенда) | `rm_probe=35`, драйвер 0 | **процесс умер `0xC0000005`** |

Итого: начиная с выпуска 2026.10.20.01 проба GPU роняет процесс на ЛЮБОЙ машине без драйвера NVIDIA
(и со сломанным драйвером). До 15c414b2 это и роняло приложение на кнопке «Матрица отклика...». После
15c414b2 падает только дочерний процесс, но подсказка говорит «проверка GPU упала в драйвере Nvidia…» тем,
у кого видеокарты Nvidia нет вовсе, и каждый сеанс оставляет событие о сбое в журнале Windows. С драйвером
старее 580 (ветка CUDA 12) сборку 13.4 проверить нечем: такого драйвера на машине нет.

### Правка: предпроверка драйвера до загрузки библиотеки

Решение Amber 23.10.2026, дословно: «Понятно. Делай базовые проверки сначала, что у пользователя вообще
есть Cuda какой-то версии. И только потом грузи библиотеку.»

Что ответит сам драйвер, проверено стендом заранее (`drvcheck`, тот же `LoadLibraryExA(nvcuda.dll, 0x800)`):
исправный — `cuDriverGetVersion` 0 / 13040, `cuInit` 0, `cuDeviceGetCount` 0 / 1; сломанный (заглушка
грузится, реализация нет) — все три отвечают 100, без сбоя. То есть API драйвера безопасно там, где
рантайм 13.4 падает.

* `RmGpu.CheckDriver` — первым делом `Probe`, до `LoadLibrary(rmgpu_f.dll)`: `nvcuda.dll` из System32,
  `cuDriverGetVersion`, `cuInit(0)`, `cuDeviceGetCount`. Нет файла, нет вызовов, 100, версия 0, 0
  устройств — `NoDevice` (подсказка «видеокарта Nvidia с поддержкой CUDA не найдена…»); драйвер с CUDA
  старше 13.0 — `DriverTooOld`; иной код — `RuntimeError`. Шаги — в журнале дочерней пробы.
* `RmGpu.LinkedCudaRuntime = 13040` — нужная версия известна до загрузки DLL; шестая сверка
  `check_gpu_dll.py` держит её равной `cudart=` паспорта (самопроверка: отставшая константа и пропавшая —
  отказ).
* `RmGpu.ProbeDriver(путь)` и `GpuAppProbeP253 --mode=driver[=<nvcuda.dll>]` — предпроверка отдельно,
  с поддельным драйвером для контроля.

Контроль поддельными `nvcuda.dll` (`--mode=driver=…`):

| драйвер | ответ |
|---|---|
| настоящий из System32 | годен, драйвер 13040, устройств 1 |
| файла нет | `NoDevice` «no NVIDIA driver installed (… Win32 error 126)» |
| чужой `nvcuda.dll` без экспортов | `NoDevice` «the NVIDIA driver is broken…» |
| `cuDriverGetVersion` = 12080 | `DriverTooOld` «supports CUDA 12.8, the library needs CUDA 13.0 or newer» |
| версия 0 | `NoDevice` |
| `cuInit` = 100 | `NoDevice` |
| устройств 0 | `NoDevice` «the driver sees no device» |
| `cuInit` = 999 | `RuntimeError` «cuInit returned 999» |

Полная проба с настоящим драйвером: дочерним процессом — годна (RTX 3070 Laptop, 0.13 с), в своём —
годна. Окно матрицы (`--mode=form`): поставочная DLL — галка годна, ISO — недоступна; падающая DLL — по-
прежнему `ProbeCrashed 0xC0000005` (ветка `AMBER261` цела). Экраном (Release, копия конфига): окно
открылось, галка годна, подсказка с RTX 3070, строка журнала `GPU check … available`; исходная
конфигурация — 0 расхождений.

⚠ Случай «драйвера нет» целиком через приложение на этой машине не воспроизвести: System32 не спрятать.
Доказательство из двух частей: стенд — рантайм 13.4 падает ровно когда его `LoadLibraryExA(nvcuda.dll,
0x800)` не находит файл; предпроверка делает тот же вызов первой и на поддельном «нет файла» отказывает
`NoDevice`, не доходя до библиотеки.

## Что осталось

* Что именно падает на машине пользователя, неизвестно: GPU, драйвер и ОС там не названы. После
  обновления причину покажет журнал приложения (строка `GPU check` с шагом и кодом), а событие 1000
  Application Error в журнале Windows назовёт сбойный модуль. Окно и приложение падать перестанут
  при любом ответе.
* Исправление доедет до пользователя только с выпуском. Версию по слову Amber («Только коммит») не
  поднимали.
