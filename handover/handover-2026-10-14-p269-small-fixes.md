## 1. Поле «предел счёта» окна «Настройки»

**Причина.** `numericUpDown13` (`ChartViewConfig.CountLimit`, `int`): в разметке `Maximum =
decimal.MaxValue`, `SaveFormContents` пишет `(int)Value` — то же, что П268 сняла у периода
автосохранения. Снизу поле пускало 0, а при пределе 0 сглаживание
(`SpectrumAriphmetics.GetWindowSize`) на пустом канале считает окно 0/0 = NaN, и `Convert.ToInt32`
бросает `OverflowException` (из `Parallel.For` — `AggregateException`).

**Правка.** `GlobalConfigForm.LimitCountLimitField` (рядом с `LimitAutosavePeriodField`, зовётся из
обоих конструкторов): `Minimum = 1`, `Maximum = int.MaxValue`. Разметка и `.resx` не тронуты.

**Обход.** Все 13 числовых полей формы получили «3000000000» → «ОК»: до — отказ только у
`numericUpDown13` (`numericUpDown10` уже починила П268); у прочих полей пределы 50…10⁷ — поле само
сводит набранное к пределу. Во всём приложении `decimal.MaxValue` в пределах полей разметки было
ровно у двух полей (`numericUpDown10`, `numericUpDown13` в `GlobalConfigForm.Designer.cs`); в коде —
только `NuclideDefinitionForm.textColumn2/3` (полоса П266, значение уходит в `double` — переполнения
нет). `DeviceConfigForm`: `decimal.MaxValue` нет, наибольший предел — 65535 (`numberColumn2`).

| набрано / из файла настроек | до | после |
|---|---|---|
| 10 / 100 / 1000 / 2147483647 / 1 | записано то же | то же |
| 2147483648, 3000000000 | «ОК» — `OverflowException` | 2147483647 |
| 0, −5 (набрано) | записано 0 → сглаживание `OverflowException` | 1, сглаживание проходит |
| файл настроек 0, −5 → окно → «ОК» | 0 → сглаживание `OverflowException` | 1 |

Контроль: сглаживание с пределом 0 бросает в обеих сборках (механизм жив; защищает поле). Код
пробы: до 1 (7 дефектов), после 0.

## 3. `FillAbsentTimes`: начало из времени пробы позже конца

**Причина.** Начала нет, проба и конец есть — начало = проба (П263, задержка ноль), и при пробе позже
конца начало выходило ПОЗЖЕ конца: длительность набора отрицательная, поправка на распад молча 1.

**Правка.** `DocumentManager.StartNotAfterEnd`: в этом раскладе начало не позже «конец − полное
время» (набор длиной T, кончившийся в конце, начался не позже конца − T); без полного времени (0,
∞, NaN) — не позже конца. Проба раньше «конца − T» — правило П263 дословно. Голос `A207` — как у П263
(время пробы есть, начало не «неизвестно»). ⚠ Граница взята «конец − T», а не «конец»: проба внутри
набора давала набор короче собственного полного времени — тот же разлад.

Замер `--mode=filltimes` на `RC103_Charoite` (в самом файле проба 08.02 12:47 позже конца 08.02 09:41,
конец − начало = T = 76364 с):

| расклад | до | после |
|---|---|---|
| F1 начала нет (проба позже конца) | начало 08.02 12:47 > конца, конец − начало −11187 с, Co-60 ×1.000000 | начало = конец − T = 07.02 12:28:49 — ровно исходное начало файла; Co-60 ×0.999794 как у полного файла; сохранение пишет это начало |
| F2 проба внутри набора (конец − T/2) | начало = проба, набор 38182 с < T | начало = конец − T, Co-60 ×1.000000 |
| F3 проба раньше набора (конец − 2T) | начало = проба | то же (правило П263) |
| F4 без начала и конца | начало = проба, конец + T | то же |
| F5 полное время 0 / NaN | начало позже конца | начало = конец |
| LoadDocument(F1) | начало позже конца | = конец − T |

Код пробы: до 1 (5 дефектов), после 0; F0/F3/F4/F6 одинаковы в обеих сборках. В данных такого
расклада нет: из 907 спектров (блоков `ResultData`) корпуса и `YandexDisk\Спектры` ни у одного нет
начала при наличии конца (сканер `D:\BqMoni_Claude\p269\scan_times.py`).

**Круг корпуса** пробой П263 (`--mode=xml --keep`, 136 файлов) обеими сборками: открыто 136/136,
круг 0 расхождений; 272 сохранённых файла «после» побайтно равны 272 «до» (контроль изменённого
байта виден).
