## 1. Расхождение посылки строки с реальностью

**Строка говорит: «шапка DLL не несёт `MEASBEGIN`… поэтому `to_xml` кладёт
пустые `<Time>`, `<StartTime>`». Про `MEASBEGIN` верно, про ВРЕМЯ — уже
реальности.** Шапка DLL целиком (134 байта, семь ключей):

    DATE=20-05-2010
    TIME=12:15:11
    TLIVE=200
    TREAL=200
    ENERGY=1, 0, 3
    FWHM=2, -0.0324826, 1.93201, -5.94901e-05
    COMMENT= A= 1000 Bq

Время там **есть** — просто в ключах ДЕМОНСТРАЦИОННОГО диалекта (`DATE`/`TIME`),
которых `to_xml` не читает. То есть файл DLL по шапке — не «свой третий
диалект», а половина демонстрационного: `DATE`/`TIME` от него, `WEIGHT`/`VOLUME`
нет ни от кого.

⛔ **И верить этому времени всё равно нельзя: это зашитая в DLL константа.**
Измерено, а не предположено: два прогона подряд 05.09.2026 (A = 1000 Бк и
A = 2000 Бк, разные `TLIVE` 200 и 100) дали в шапке **одну и ту же**
`DATE=20-05-2010`, `TIME=12:15:11`. Прогон был в сентябре 2026-го.

Отсюда решение (моё, обоснование выше): **`DATE`/`TIME` шапки НЕ читать**, а
временем ставить запись файла. Плюс ключ `--when`, закрепляющий время: у файла,
положенного в git, время записи своё, а не DLL, и без закрепления XML перестаёт
быть воспроизводимым. Для пары в дереве закреплено `2026-09-05T11:05:18.845237`
и `…851132` — настоящие моменты записи прогоном.

## 4. Пункт 3 — поверка, которая ОТКАЗЫВАЕТ. Это суть строки

Было: одна поверка, «сумма = `CPS`·`TLIVE`», под условием `if cps and live > 0`.
Ключа `CPS` в шапке DLL нет — условие не исполнялось, спектр брался
непроверенным, **и выглядело это как «проверка прошла»**.

Стало: поверка выбирает тождество по диалекту шапки, а **не найдя ни одного —
ОТКАЗЫВАЕТ**.

* `CPS` есть → как раньше, сумма против `CPS`·`TLIVE` (поверочный диалект);
* `CPS` нет, а сцена назвала число распадов → **две половины, порознь**:
  * шапка: `A · TLIVE = N`, где `A` берётся из `COMMENT= A= N Bq`;
  * тело: `0 ≤ Σ отсчётов ≤ N` — один распад не даёт в спектр больше одного
    события;
* иначе → отказ с перечислением того, чего не хватает.

**Допуск тождества — относительный, 10⁻³, и число выбрано замером, а не на
глаз.** `TLIVE` печатается DLL с ограниченным числом знаков; на неделящемся
нацело отношении (200 000 / 3000 = 66.6667) обрезка даёт относительную ошибку
5·10⁻⁷. Допуск 10⁻³ покрывает её с запасом в три порядка и при этом ловит
подмену времени: на сцене он равен 200 распадам при расхождении 10 000.

⚠ Половины разные по существу и потому написаны порознь: первая судит ШАПКУ,
вторая — РАЗБОР ДВОИЧНОГО БЛОКА. Прежняя `CPS`-ная делала только вторую работу;
сложить их в одно число значило бы получить «ошибок нет» из двух ошибок в
разные стороны.

## 5. ПШПВ: правило ЛСРМ-ветки здесь не работает

`to_xml` намеренно НЕ переносит модель ПШПВ — «корпус меряет разрешение сам по
спектрам, и чужая модель спорила бы с измеренной». Для спектра из DLL это
неверно: разрешение здесь **вход сцены** (блок `AN_*`), оно известно точно, и
измерять его по спектру — мерить свой же вход с шумом.

Семейства при этом разные: DLL пишет ПШПВ(E) = c0 + c1·√E + c2·E в кэВ,
приложение хранит ПШПВ(канал) = √(a + b·ch + c·ch²) в каналах. Точного перевода
нет — **и это измерено, а не оценено**: у DLL главный член ровно c1·√E, значит
ПШПВ² линейна по каналу, и три параметра ложатся почти без остатка.

    a = −0.049761056,  b = 1.2412464,  c = −1.9459934·10⁻⁶

| энергия | DLL | приближение | расхождение |
|---|---|---|---|
| 60 кэВ | 14.929 | 14.932 | +0.020 % |
| 122 кэВ | 21.300 | 21.303 | +0.014 % |
| 662 кэВ | 49.638 | 49.637 | −0.001 % |
| 1332 кэВ | 70.400 | 70.400 | −0.000 % |
| 2614 кэВ | 98.590 | 98.591 | +0.000 % |

Худшее по ВСЕЙ шкале — **1.178 %, и оно на канале 1 (3 кэВ)**, ниже любого
рабочего порога (`Min_Range` конфигурации 30 кэВ). Число уходит в `<Note>`
вместе с исходным `FWHM=`: молча приближать чужую модель нельзя.
