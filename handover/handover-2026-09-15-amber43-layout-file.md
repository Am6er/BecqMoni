Задача Amber 15.09.2026, консоль с журналом падения
([amber43/crashlog-2026-09-15.txt](amber43/crashlog-2026-09-15.txt)), дословно:

> «Заведи задачу в AMBER. Падение приложения, если файл настроек расположения
> окон в UI поломался при сохранении. Основная задача - избежать поломки этого
> файла ExpertMode.xml»

Решения Amber того же дня, вопросником (скилл `analyst`), дословно:

* объём — **«Только записать»** (эта запись и строка; починка — отдельным заходом);
* при сломанном файле на запуске — **«Не падать: отложить сломанный, поднять
  `.bak`, иначе умолчание; сказать окном после показа (рекомендую)»**.

## Что в журнале падения

`System.Xml.XmlException: Root element is missing` из
`DockPanel.Persistor.LoadFromXml(DockPanel, Stream, …)` ←
`MainForm.MainForm_Load` (`MainForm.cs:218` сборки `2026.7.24.2`, автономная
установка `M:\Tmp\2\Spectre\BecqMoni`). «Root element is missing» — файл пуст
или обрезан до первого элемента: у XML нет корня. Исключение поднимается из
`OnLoad`, ловить его некому — приложение падает **на каждом запуске**, пока файл
не удалят руками.

## Механизм поломки при записи — измерено по IL библиотеки

`DockPanel.Persistor.SaveAsXml(DockPanel, string, Encoding)` (DockPanelSuite
3.1.1, `WeifenLuo.WinFormsUI.Docking.dll` из сборки): IL —
`ldc.i4.2` → `newobj FileStream(String, FileMode)` → `call SaveAsXml(DockPanel,
Stream, Encoding)`, то есть **`new FileStream(fileName, FileMode.Create)`: файл
сперва обрезается до нуля, и только потом в него пишется раскладка**. Процесс,
остановленный между этими двумя шагами, оставляет пустой файл — ровно то, что в
журнале. Как останавливается:

* завершение сеанса Windows: `MainForm_FormClosing` идёт и при
  `CloseReason.WindowsShutDown`, а система убивает приложение по своему сроку;
* исключение внутри сериализации (содержимое панели с отказавшим
  `GetPersistString`, освобождённый контрол): до ~~`A13`~~ (28.08.2026) оно
  съедалось пустым `catch` — файл к тому моменту уже обрезан; сборка из журнала
  (`2026.7.24.2`) старше этой правки;
* переполненный диск, снятие доступа — частичный файл.

~~`A13`~~ закрыла МОЛЧАНИЕ об отказе записи, но не саму поломку: отказ теперь
называется, а обрезанный файл остаётся и валит следующий запуск.

## Сделать (не делалось — режим «только записать»)

1. **Атомарная запись** во всех трёх местах и у спасательной копии: раскладку
   сериализовать в память (`dockPanel1.SaveAsXml(Stream, Encoding)` —
   перегрузка в библиотеке есть, проверено отражением), затем во временный файл
   рядом (`ExpertMode.xml.tmp`), `Flush`, и подменить `File.Replace(tmp, target,
   target + ".bak")` — прежняя удачная копия остаётся `.bak`; если целевого файла
   ещё нет — `File.Move`. Отказ сериализации тогда не трогает файл вовсе, а
   убитый процесс оставляет либо старый файл, либо новый, но не пустой.
2. **Заслон на чтении** (решение Amber): `LoadFromXml` под `try`; при отказе —
   сломанный файл переименовать в `ExpertMode.xml.broken-<yyyyMMdd-HHmmss>`
   (улика остаётся), попробовать `.bak`; если и он негоден — раскладка по
   умолчанию; сообщение с путями и причиной показать **после показа окна**
   (`base.Shown`, как записка ~~`A13`~~ в `MainForm_ShownReportLayout`), ресурсы в
   двух языках. То же в двух пунктах меню (там человек на месте — окно сразу).
3. **Приёмка — проба** без окон (`AppUi.HasWindows == false` → отказ чтения
   должен быть назван исключением/кодом, не молчать): (а) подсадка пустого файла
   и файла, обрезанного посередине, — путь чтения не бросает
   `XmlException`, сломанный переименован, `.bak` поднят, умолчание при его
   отсутствии; (б) запись с подсаженным отказом сериализации (или остановом
   между шагами) — целевой файл остаётся прежним и читаемым, `.tmp` убран;
   (в) удачная запись — `.bak` равен прежнему файлу побайтно; положительный
   контроль — старая сборка на (а) бросает `XmlException`, на (б) оставляет
   пустой файл. Плюс проверка `check_headless.py` (новые окна — только на
   оконном пути).

Родня: ~~`A13`~~ (читатель отказа записи), `A4`/`A9` (молчаливые отказы
приложения).
