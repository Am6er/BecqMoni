## Ловушка задания: подставить ресурс КАК ЕСТЬ было нельзя

**Что дословно говорил литерал** (`N42/Util.cs:516` до правки):

```
N42 EnergyBoundaryValues not supported. Only calibration coefficients supported. Using default calibration y=x.
```

**Что код делает на самом деле в этой ветке.** Разбор коэффициентов обёрнут
`try`, в начале которого стоит
`resultData.EnergySpectrum.EnergyCalibration = new PolynomialEnergyCalibration()`.
Конструктор `PolynomialEnergyCalibration` (проверено в исходнике) ставит
`polynomialOrder = 1` и `coefficients = { 0, 1 }` — то есть **ровно y = x**.
Поэтому в оконном запуске, где `catch` печатает сообщение и работа
ПРОДОЛЖАЕТСЯ, документ уходит дальше со шкалой y = x: номер канала объявлен
энергией. В безоконном запуске до подстановки дело не доходит вовсе — `throw`
из `catch` уходит наружу, минуя остаток блока.

**Что говорило ЗНАЧЕНИЕ КЛЮЧА** `ERRUnsupportedEnergyBoundaryN42` (обе культуры,
прочитано ИЗ СТАРОЙ СБОРКИ отражением):

| культура | было |
|---|---|
| нейтральная | `N42 EnergyBoundaryValues not supported. Using current calibration.` |
| `ru` | `Объект спецификации N42 - EnergyBoundaryValues не поддерживается в приложении. Используйте калибровки полиномом.` |

Английское «Using current calibration» — **неправда**: текущая калибровка не
используется, ставится ВСЕГДА y = x. Русское значение о том, что произошло, не
говорит вовсе (это совет, а не сообщение). Подстановка ресурса без правки
значения сменила бы верный текст литерала на неверный: молчание превратилось бы
в уверенную неправду.

## Как приведены значения (`A138`)

Английский первичен; оба значения говорят одно и то же и оба описывают
поведение — ту его половину, в которой этот текст вообще показывается.

| культура | стало |
|---|---|
| нейтральная | `N42 EnergyBoundaryValues not supported. Only calibration coefficients are supported. Using the default calibration y=x: the channel number is taken as the energy.` |
| `ru` | `Объект спецификации N42 - EnergyBoundaryValues не поддерживается: читаются только коэффициенты полинома. Подставлена калибровка по умолчанию y=x: номер канала принят за энергию.` |

Оговорка «номер канала принят за энергию» добавлена нарочно и не является
украшением: это и есть последствие подстановки, и ровно теми же словами
называют его закрытые ~~`A95`~~ и ~~`A114`~~. Второго соглашения о том, как
называется y = x, в дереве не заводится.

⚠ Текст по-прежнему называет ОДНУ причину (`EnergyBoundaryValues`) для целого
класса отказов разбора калибровки — это открытая `A136`, и заход её не трогал
нарочно: поведение меняться не должно было.

## Что сделано по `A137` и ПОЧЕМУ именно так

**Решение: отказывать без окон, говорить вслух и продолжать в окнах — то есть
ТО ЖЕ соглашение, что у соседнего `catch`. Третьего поведения не заведено.**

Соседний `catch` (`N42/Util.cs:547` после правки) устроен так: `!AppUi.HasWindows`
→ `throw new InvalidOperationException(...)`; иначе `AppUi.Report(text, ...)` и
работа продолжается. Дверь на отсутствующей калибровке написана точно так же:

```csharp
if (rad.EnergyCalibration == null)
{
    if (!AppUi.HasWindows)
    {
        throw new InvalidOperationException(
            "BecqMoni: в файле N42 нет энергетической калибровки (" + AppUi.Where(filename)
            + "): подстановка y = x объявляет номер канала энергией — считать по такому спектру нельзя.");
    }
    AppUi.Report(Resources.ERRNoEnergyCalibrationN42, "", MessageBoxIcon.None);
}
```

Довод тот же, которым закрыта ~~`A95`~~: подставить калибровку значит объявить
номер канала энергией, а молча этого делать нельзя. Без окон читателя у
предупреждения нет, поэтому читателем становится код возврата.

**Проверка стоит ДО цикла нарочно.** `rad.EnergyCalibration == null` — свойство
ВСЕГО файла, а не отдельного измерения; внутри цикла оно сказалось бы по числу
спектров в файле. Подстановка `CoefficientValues = "0 1"` внутри цикла оставлена
как была: поведение оконного запуска не меняется.

⚠ Новая пользовательская строка ЗАВЕДЕНА (`ERRNoEnergyCalibrationN42`, обе
культуры) — в отличие от ~~`A95`~~, где обошлись уже переведёнными. Подходящей
готовой не нашлось: `CalibrationFunctionError` говорит про немонотонную функцию,
`ERRUnsupportedEnergyBoundaryN42` — про границы энергий; взять любую из них
значило бы повторить дефект `A136` (называть причину, которой не было).

### Что зовёт СОБРАННЫЙ метод — разбор IL, а не исходника

Оконная половина двери (`AppUi.Report`) в безоконной пробе не исполняется, и
доказать замером «литерала больше нет, читается ресурс» поведением нельзя.
Поэтому проба разбирает **IL собранного** `Util.ImportFromN42(RadInstrumentData, …)`
настоящим проходом по опкодам (таблица опкодов строится из
`System.Reflection.Emit.OpCodes`, токены разрешаются `Module.ResolveString` /
`Module.ResolveMethod`) — то есть мерится артефакт, а не текст.

| | старая сборка | новая |

| обращений к `Resources` из метода | 2 (обе — `get_CalibrationFunctionError`) | 4 (`get_CalibrationFunctionError` ×2, `get_ERRUnsupportedEnergyBoundaryN42`, `get_ERRNoEnergyCalibrationN42`) |
| литерал `N42 EnergyBoundaryValues not supported. Only calibration coefficients supported. Using default calibration y=x.` | **ЕСТЬ** | **НЕТ** |
| строковых литералов в методе | 24 | 26 (ушёл английский, пришли две части русского отказа `A137`) |

## Новые находки, измеренные по ходу

1. **`throw new Exception()` без сообщения** — `N42/Util.cs:492` (2012) и `:297`
   (2006), обе при пустом списке коэффициентов. Замер входа Б: безоконный отказ
   доезжает до человека строкой «Выдано исключение типа "System.Exception"» —
   она не называет НИЧЕГО. Это НЕ `A136` (та про оконный текст `catch`), а про
   само бросаемое исключение.
2. **`RadiologicalInstrumentData`: y = x молча и `CheckCalibration` не зовётся
   вовсе** — `N42/Util.cs:158…218`. Калибровка строится подгонкой по точкам
   файла только при `listCalibration.Count >= 5`; иначе в документ уходит
   `new PolynomialEnergyCalibration()`, то есть y = x, и об этом не говорится.
   Сверх того, подогнанный полином 4-го порядка на этом пути НЕ ПРОВЕРЯЕТСЯ
   `CheckCalibration` — в отличие от обоих соседних путей.
3. **`double.Parse` без культуры** — `N42/Util.cs:506` и `:313`. Замер (вход
   В-бис, тот же здоровый файл под культурой `ru-RU`): `FormatException`,
   «Входная строка имела неверный формат», ввоз отказывает целиком. ⚠ В окнах
   это сегодня НЕ проявляется: `MainForm.cs:162–164` ставит
   `NumberDecimalSeparator = "."` глобально при запуске. То есть разбор файла
   держится на настройке, сделанной в другом месте и по другому поводу, и любой
   безоконный вызывающий (проба, харнесс) на нём спотыкается.
4. **Настоящего файла N42 в дереве нет ни одного** — ни один замер ввоза N42 не
   проверен против того, что реально пишут приборы. Все входы этого захода
   сочинены.
