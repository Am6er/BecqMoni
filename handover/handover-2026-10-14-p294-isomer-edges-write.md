## Скрипт и запись

`tools/nucdb/add_isomer_edges.py` — скрипт П282, перенесённый в дерево (путь дерева — от `__file__`, CSV — только
ключом `--csv`), с новым шагом `drop_zero_rows`: после расщепления до неподвижной точки удаляются ТОЛЬКО строки
P → D, которые расщепление этого прогона довело до нуля (записываются в момент правки), и только если (а) строка ещё
числовой нуль, (б) рядом её пара P → X с долей > 0, (в) правило приложения (`ChainTable` + `ChainLevelClause` +
`ChainPercColumn`, текст из `DecayParentRule.cs`) после удаления даёт P ровно прежние ветви без нулевой строки.
Нарушено (в) — откат в точку сохранения, строка остаётся, печать ⛔. В конце — сверка набора нулевых строк (было +
оставленные) и проверка неподвижной точки: план по записанной базе пишется в точке сохранения и откатывается — 0
вставок, 0 правок.

## Нулевые строки расщепления: удалено 9, оставлено 3

У трёх родителей под ТЕМ ЖЕ именем в ту же дочь лежит вторая строка — распад изомера родителя на его уровне:

| родитель | строки `decay_chain` в D | что даёт правило без нулевой строки |
|---|---|---|
| `130SN` | ур.0 → 130SB 100 (поставка → 0), ур.2 → 130SB 100 (130SNm) | 130SB 100 (ур.2) **и** 130SBm 100 |
| `52FE` | ур.0 → 52MN 100 (→ 0), ур.42 → 52MN 100 (52FEm) | 52MN 100 (ур.42) **и** 52MNm 100 |
| `85Y` | ур.0 → 85SR 100 (→ 0), ур.1 → 85SR 100 (85Ym) | 85SR 100 (ур.1) **и** 85SRm1 100 |

`ChainLevelClause` берёт строку своего уровня родителя в эту дочь, а нет её — «наименьший уровень тройки», то есть
строку изомера: ряд получил бы P → D 100 % рядом с P → X 100 % — ровно то удвоение, от которого метод расщеплением и
защищается. Нулевая строка уровня 0 держит выбор на уровне 0, поэтому оставлена; скрипт откатил её удаление сам
(проверка (в)). Следствие для человека: карточка NucBase у этих трёх по-прежнему пишет «130SB 0 [β-]», «52MN 0
[EC β+]», «85SR 0 [EC β+]» (проба ниже); у девяти прочих строки «0» больше нет.
