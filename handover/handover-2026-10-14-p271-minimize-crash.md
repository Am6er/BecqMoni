## 1. ⛔ Сворачивание главного окна убивало процесс (правка П259, `b69e91ac`)

**Причина.** При сворачивании главного окна DockPanelSuite (`DockingMdi`) отдаёт документу размер 0×0 (замер П270,
`MinimizeProbe`). `EnergySpectrumView_SizeChanged` в режиме «Fit» (правка П259) звал `FitHorizontalScale`, а она
не проверяла ширину поля: `(Width − 40 − 18 − 4) / (…)` при ширине 0 — масштаб −0.058. Дальше — `ScrollBar`:
`hScrollBar1.Maximum = num2 < 0` опускает `Minimum` до `num2` и ставит `Value = num2` → `ValueChanged` →
`RefreshViewportData` → `RecalcScrollBar` (вертикаль MinMax) → `Minimum = 0` (поле `value` молча становится 0) →
`Maximum = num2` → снова `Value = num2` → … — `StackOverflowException` (0xC00000FD), процесс падает без окна, со всем
несохранённым и с идущим набором. «Fit» + MinMax — умолчание и поставки, и конфига Amber.

Граница: поле графика — `Width − 62`. На 60 px масштаб −0.0019, правый край `(int)(−0.98) + 5 = 5` > 0 — не падает
(контроль П270), но масштаб отрицательный, график пуст. На ≤ ~57 px — падение. Тем же путём падали ещё два входа,
которых П270 не называла: **документ, открытый при свёрнутом окне** (`SetDefaultHorizontalScale` /
`FitHorizontalScale` при 0×0 — зовёт `MainForm` при открытии) и **увеличение выделения (клавиша M)** в сжатой панели
(`ZoominSelectedRegion` при `width ≤ 0`; старый путь, не П259).

**Правка** (`BecquerelMonitor/EnergySpectrumView.cs`):
* `FitFieldWidth()` — ширина поля подгонки (одна формула вместо двух копий).
* `EnergySpectrumView_SizeChanged` — подгонка только при `FitFieldWidth() > 0`. Масштаб прежней подгонки остаётся и
  совпадает с `lastFitHorizontalScale`, поэтому разворот на настоящее поле вписывает спектр той же веткой.
* `FitHorizontalScale`, `SetDefaultHorizontalScale` (умолчание «Fit») — при поле ≤ 0 масштаб не трогается, подгонка
  откладывается до поля (`DeferFitUntilFieldExists`: масштаб помечается подгонкой, полоса в 0) — документ, открытый
  при свёрнутом окне, при развороте вписывается. Умолчание «Equal» — как было.
* `ZoominSelectedRegion` — при `width ≤ 0` выход.
* `RecalcScrollBar` (защита в глубину) — ветка прокрутки только при `num2 > 0`: правый край левее нуля — прокручивать
  нечего, полоса выключается (`Maximum = Minimum = Value = 0`). При обычных размерах `num2 ≥ 5`, условие не меняет
  ничего.

`DocEnergySpectrum.cs` проверен на тот же нулевой размер и **не менялся**: `DocEnergySpectrum_SizeChanged` пуст, поле
масштаба (эхо гасит П259, `View_ActionEvent`) при нулевом поле событий не получает — подгонки нет; после разворота
поле то же (замер ниже, сцена `dock`).

## 2. Окно результата могло встать на «FSA: computing…» после быстрой смены вкладки (правка П261, `d4af1d26`)

**Причина.** `DCPeakDetectionView.UpdatePeakDetectionResult`, ветка `refreshPending`: повтор поиска для активного
спектра X запускается, затем отметки очереди снимаются с `searched = false`. Если повтор кончается СРАЗУ, без await
(нет калибровки ПШПВ — ранний выход; бросок до поиска), его собственный конец (`true`) не последний, и последней
отметкой X оказывается отметка очереди с `false` → `FsaAnalysisSession.PeakSearchEnded` выбрасывает отложенный счёт
молча, `Completed` не приходит, окно результата стоит на «FSA: computing…», отчёт — «расчёта не было».

**Правка** (`DCPeakDetectionView.cs`, `UpdatePeakDetectionResult`, `finally`): спектр, который повтор ищет (активный
— повтор берёт его синхронно, до первого await), снимается с очереди с `true`; ушедшие с экрана — по-прежнему `false`.
Если повтор ещё идёт, отметка очереди не последняя и флаг ни на что не влияет — конец даст сам повтор (`true`).
`FsaAnalysisSession.cs` не менялся.

**Проба** `FsaSessionStatesProbeP261` — новая сцена `requeue`: порядок `busy` (поиск прежней вкладки не вернулся,
поиск новой встал в очередь, первый проход разбора без пиков отложен), калибровка ПШПВ новой вкладки снимается ПОСЛЕ
первого прохода — повтор поиска кончается на раннем выходе без await. ⚠ Спектр без калибровки С САМОГО НАЧАЛА порядок
не воспроизводит (замер П271, первый вариант сцены — «сошлось» и до правки): разбор отказывает за миллисекунды, раньше,
чем спектр встанет в очередь поиска, и отказ публикуется сразу. Поэтому в приложении беда редкая (вход сменился между
первым проходом и повтором, бросок до await), но правка закрывает порядок целиком.

## 3. κ пар могла остаться считать в фоне (правка П253, `595270f8`)

**Причина.** `GpuBuild.Build` (`EfficiencyMaker/GpuMatrixRun.cs`): между двумя защитами `catch { StopJoint; throw; }`
стояли отчёт хода после узлов `report(grid.Length, …)`, журнал, `ResponseMatrix.ComputeStamp`, `NormalizationOf`,
`AngularAttenuation.FromMoments` — бросок любого из них уходил наружу, а κ на ЦП продолжала считать.

**Правка.** Всё до ожидания κ — узлы, отчёт после узлов, журнал, сборка матрицы, `RebuildTotals`,
`FillResolutionPeak` — под одной защитой со `StopJoint`; ожидание κ и перенос полей `Joint*` — как были.

(`SettledNodes = grid.Length`) — ровно незащищённое место.
