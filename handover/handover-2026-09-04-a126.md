### Что написано

Правило РАСШИРЕНО, второго не заведено: те же плечи английского письма
(кириллица = подмена, самозванец в единице), меняется только источник значения.

берут не путь, а ряд пар «имя — значение», и `*.Designer.cs` подаёт в них свой.

Добавлено:

* `literals(line)` — строковые литералы ОДНОЙ строки C#, разбор ПОСИМВОЛЬНЫЙ.
  Выражением тут нельзя: в дереве есть `this.linkLabel.Text = "http://…"`

  знаковый литерал `'"'`, отрезает `//` и `/*`.

  `/// Looks up a localized string similar to …` (многострочная — до
  `</summary>`, находка называет строку ГОЛОВЫ и имя СВОЙСТВА) и литерал в не
  закомментированной строке (находка называет строку и цель присваивания).
* В `main` — третий проход по `**/*.Designer.cs`, находка печатается с номером
  строки: `путь.cs:582 | DeadTimeLblText | самозванец в единице`.

### (б) `ERRCannotRetrieveDeviceData` — СНЯТ

Читателей ноль — перепроверено сплошным поиском по ВСЕМУ дереву в ОБОИХ
написаниях (`Retrieve` и старое `Retreive`), включая `tools/` и пробы: вне
`Properties/*` и журналов ни одного вхождения.

Снято побайтово: свойство с шапкой `/// <summary>` из `Resources.Designer.cs`
(403 байта, 10 строк со строки 891), узел из `Resources.resx` (173 байта) и из
`Resources.ru.resx` (166 байт). Скрипт задавал ожидаемое число вхождений
заранее и отказался бы при несовпадении; CRLF и BOM сохранены, счёт строк
сверен.

**Обратное чтение из СОБРАННЫХ сборок, ДВА ОТДЕЛЬНЫХ процесса** (две
одноимённые сборки в один процесс .NET не грузятся):

| сборка | ключей нейтральных | ключей в `ru` | снятый ключ | оставшийся |

| `bin\Debug_A130` (до, 17:00) | 693 | 642 | **есть** | есть |
| `bin\Debug_A126` (после, 19:13) | 692 | 641 | **нет** | есть |

Свойства `ERRCannotRetrieveDeviceData` в классе после правки тоже нет, а
`ERRUnsupportedEnergyBoundaryN42` на месте и читается обеими культурами.

⚠ Плечо «до» здесь не украшение, а положительный контроль: первый заход этой
проверки упал на перегрузке `GetProperty(string, Type)` вместо
`GetProperty(string, BindingFlags)`, `$rm` вышел `null` — и строка «свойство
… в классе: False» напечаталась бы как УСПЕХ. Поймало то, что проверка требует

### (а) `ERRUnsupportedEnergyBoundaryN42` — ОСТАВЛЕН; посылка строки оказалась неверной

**Что показал `710ac2ba`** (08.08.2022, «Replace N42 import file spectrum
method»). Он вынес из `DocumentManager` весь рукописный разбор N42-2012 (−99
строк) и заменил его на `util.ImportFromN42(...)`. Среди снятого был и

```csharp
catch { MessageBox.Show(Resources.ERRUnsuportedEnergyBoundaryN42); }
```

вокруг чтения `EnergyCalibration[0].CoefficientValues`. То есть проверялось не
«какая-то граница энергии», а вот что: **шкала в файле задана не полиномом**
(в N42-2011/2012 `EnergyCalibration` может нести либо `CoefficientValues`, либо
`EnergyBoundaryValues` — список энергий границ каналов), а приложение умеет
только полином порядка ≤ 4.

⛔ **Но сообщение при этом НЕ пропало, и это меняет посылку строки.** Тот же
`git show 710ac2ba^:BecquerelMonitor/N42/Util.cs` показывает, что ДО этого
коммита в `Util.cs` уже стоял тот же текст ЖЁСТКИМ ЛИТЕРАЛОМ:

```csharp
MessageBox.Show("N42 EnergyBoundaryValues not supported. Using current calibration.");
```

`710ac2ba` убрал не читателя, а ДУБЛЬ разбора; выжила та ветка, которая
пользовалась литералом, а не ресурсом. Через час коммит `3e8f9d9b` («Fix.
Calibration error during import n42») переписал литерал точнее — сегодня это
`N42/Util.cs:516`:

```
"N42 EnergyBoundaryValues not supported. Only calibration coefficients supported. Using default calibration y=x."
```

Сегодня это место — уже с дверью `AppUi`: без окон бросается
`InvalidOperationException`, с окнами `AppUi.Report`. Так что **человек причину
отказа НЕ теряет; он теряет ПЕРЕВОД** — русское значение ключа лежит в
`Resources.ru.resx` и никем не читается.

**Как ведёт себя нынешний разбор в этом положении.** Он этого положения НЕ
РАЗЛИЧАЕТ, и это установлено счётом, а не на глаз: слово `EnergyBoundaryValues`
встречается во всех исходниках приложения **один раз** — в самом литерале.
В модели разбора `BecquerelMonitor/N42/EnergyCalibration.cs` объявлены только
`CoefficientValues` и `id`; `XmlSerializer` неизвестный элемент молча
пропускает, поэтому файл с `EnergyBoundaryValues` приходит с
`CoefficientValues == ""` и попадает в тот же `catch (Exception ex)`, что и
всякая другая беда с калибровкой (нечисло в коэффициентах, порядок полинома > 4
и прочее). ⚠ **Значит текст называет ОДНУ причину для целого класса отказов.**

**Поэтому читатель ключа НЕ возвращён, и проверка не выдумана** — ровно по
оговорке задания. Чтобы читатель появился по-настоящему, нужны ДВА места, и оба
ВНЕ полосы этого захода:

1. `BecquerelMonitor/N42/EnergyCalibration.cs` — завести поле
   `EnergyBoundaryValues`, чтобы разбор вообще ВИДЕЛ этот случай;
2. `BecquerelMonitor/N42/Util.cs:516` — в `catch` развести причины: непустое
   `EnergyBoundaryValues` → `Resources.ERRUnsupportedEnergyBoundaryN42`, иначе
   сообщение самого исключения.

⚠ И тогда же придётся решить, что делать с текстом ключа: он говорит «Using
current calibration», а код подставляет y = x. Точнее сегодня жёсткий литерал,
а не ресурс.

**Замер «список импортируемых N42 не изменился» ПРОВЕСТИ НЕ НА ЧЕМ, и подменять
другой формат нельзя.** В дереве **ноль** файлов N42: `find` по `*.n42`,
`*.icd1`, `*.icd` даёт 0, и сплошной просмотр 2727 xml-подобных файлов на
