# Проверки конструктора ROI (26.07.2026)

Харнесс `CatalogCheck.cs` — единственная автоматическая проверка модуля `BecquerelMonitor/RoiWizard`
и его слоя доступа к `nucdb.sqlite`. Юнит-тестового проекта в решении нет по устройству
(см. `CLAUDE.md`), поэтому проверка сделана так же, как `RjmcmcHarness` и `LibraryFitLab`:
консольная программа, собираемая `csc` против готовой сборки приложения.

## Сборка и запуск

После сборки основного проекта:

```
csc /nologo /target:exe /platform:anycpu /langversion:7.3 ^
    /out:<out>\CatalogCheck.exe /r:<out>\BecquerelMonitor.exe ^
    /r:<out>\Microsoft.Data.Sqlite.dll /r:System.dll /r:System.Core.dll ^
    /r:System.Drawing.dll /r:System.Windows.Forms.dll ^
    tools\RoiWizardCheck\CatalogCheck.cs
```

**Грабли:** без `CatalogCheck.exe.config` рядом падает `TypeInitializationException` на
`SqliteConnection` — `SQLitePCLRaw.core` не находится без привязок из
`BecquerelMonitor.exe.config`. Скопировать его под именем харнесса:

```
copy <out>\BecquerelMonitor.exe.config <out>\CatalogCheck.exe.config
```

Запускать из каталога сборки: путь к базе берётся от каталога сборки
(`AppDomain.CurrentDomain.BaseDirectory`). Код возврата 0 — всё зелёное, 1 — есть провалы.

## Что проверяется (33 утверждения)

**Данные каталога** — читается ли `nucdb.sqlite` вообще, сходятся ли линии с ENSDF:
Tl-208 2614.511 / 99.754 %, Bi-214 609.321 / 45.44 %, K-40 1460.82 / 10.66 %,
Pa-234m 1001.03 / 0.842 %.

**Ловушка `parent_l_seqno`** — линия 1001.03 кэВ Pa-234m лежит при уровне 2, и привязка
к жёсткому нулю теряла бы её целиком.

**Ветвление рядов** — сверка с эталоном `tools/LibraryFitLab/data/recommended_sets.csv`:
Tl-208 0.3594, Po-212 0.6406, Th-227 0.9862, Fr-223 0.0138; линия Tl-208 2614 на распад
Th-232 даёт 35.8516 % (цифра в цифру эталон).

**Порядок членов ряда** — обход сверху вниз, а не сортировка по доле: на порядке держится
«добавить членов ниже данного», а у Ra-228, Ac-228, Th-228 и Pb-212 доля одинаковая
(единица), и сортировка порядок уничтожала.

**Регистр в `nucid`** — `PrettyName` для 241AM / 244CM / 147PM / 152SM против 234PAm1 /
108AGm / 99TCm1. Изомер в базе всегда со строчной `m` (1077 записей), а на «m» кончаются
шесть символов элементов; поиск маркера без учёта регистра превращал **Am-241** — первый
нуклид любого калибровочного набора — в «A-241m».

**Пересчёт интенсивности при импорте из NucBase** — множитель 208TL = 0.3594, линия
583.19 кэВ ложится 30.549 % вместо 85 %; 212BI = 1.0; посторонний 137CS не масштабируется.

**Порядок критериев слияния** — контракт с `comboCriterion`: форма приводит `SelectedIndex`
прямо к перечислению, сдвиг на единицу молча подменил бы критерий.

**Состав рекомендованного сета** — воспроизводит ли `BuildRecommendedSet` эталонный сет
ASN16 Th-232 из `recommended_sets.csv` при k = 0.7 / I_min = 1 % (все 20 линий), и
попадает ли якорь U-238 (Pa-234m, 0.842 %) в сет мимо порога по интенсивности.

## Результат прогона 26.07.2026

Все 33 проверки зелёные. Загрузка каталога 248 мс, 2142 нуклида, 4 ряда, 8 семейств,
10 элементов ХРИ, 121 классифицированный нуклид.

Сверх эталона рекомендованный состав даёт две линии — Ra-228 13.5 кэВ (1.6 %) и
Bi-212 39.9 кэВ (1.06 %). Обе настоящие; эталон обрезан снизу 46.54 кэВ по диапазону
детекторов, а `LibraryPeakFitter` отсекает их по `Min_Range`.

## Найдено этим харнессом

* **`nucdb.sqlite` без единого индекса.** Сборка каталога занимала **216 секунд**:
  коррелированный подзапрос по `parent_nucid` шёл полным сканом 66 тыс. строк. С пятью
  индексами и соединением вместо подзапроса — **255 мс**, в 850 раз быстрее. Выигрывают и
  запросы NucBase, они ходят по тем же колонкам.
* **Терялись пять нуклидов** — F-18, Bi-210, Po-212/215/218: чистые α/β-излучатели, γ-линий
  в базе у них нет вовсе, а из списка семейства пропадать они не должны.
* **Сортировка членов ряда по доле** ломала «добавить членов ниже».
